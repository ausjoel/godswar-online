# Reborn database: schema map

Human summary of `glossary.json` (same folder). Both are generated by `build_glossary.py` from
`live-schema-meta.json`, a read-only snapshot of the **live** reborn database `godswar`
(PostgreSQL 17 on the VPS, read 2026-10-28 with `pg_dump -s` and `BEGIN READ ONLY` queries; no write,
no restart). Hand-written facts are in `glossary_tables.py` and `glossary_columns.py`.

* **226 tables** (225 in schema `public`, 1 in schema `legacy`), **2102 columns**, exact row
  counts as of the snapshot. The task brief said 225: that is the `public` schema alone.
* 37 views exist too (`character_equip`, `official_item_template_content`, ...). They are read-only
  projections and are listed in `glossary.json` `_meta.views`, not mapped column by column.
* Three tables (`server_rates`, `server_rates_log`, `server_rates_state`) come from our RATES patch, not
  from stock reborn.
* "CdKey" does not exist anywhere in this database. It was a field of the old 1.0 tab only.

## How to read the columns

| Field | Meaning |
|---|---|
| **edit class** | `free`: Safe to edit (for character rows: while that character is offline). Takes effect as 'applies' says.<br>`derived`: Written or recomputed by the server, or a copy the server does not read: editing is pointless or harmful.<br>`revision`: A version counter: never type a value; a write that changes the row bumps it by one.<br>`sealed`: Read-only: published content checked by hash at start-up, or evidence (ledgers, claims, audit) that triggers or exactly-once rules protect. The UI says why (read_only_reason).<br>`internal`: Server plumbing (leases, tokens, hashes, packets, archives). Never shown. |
| **applies** | `startup`: Read when the server starts (or on first use) and kept until restart: edit, then gw251 restart.<br>`login`: Loaded when the character enters the world and kept in memory while online: edit only while offline.<br>`per_use`: Read from the database each time the feature runs: a change counts from the next use.<br>`hot_reload`: Polled by the patched server every 5 s or reloaded with POST /rates/reload: live.<br>`never`: The running server does not read it (staging copy, reference copy, evidence, archive or tooling).<br>`unknown`: Not established. |
| **ref** | The kind of id a column holds (item, skill, map, pet species ...). `_meta.ref_types` in the JSON says where the names live. |
| **min / max** | From the column's own CHECK when there is one (`range_source: check`), else from the glossary, else the type's range (`range_source: type`). |
| **desc_source** | `hand` (written for this glossary), `db_comment` (the database's own comment), `generic` (shared text for a common column name). Every column has one of these three; none is described from its name alone. |

Edit-class rule used by the builder: a column is never *looser* than its table. In a `sealed`,
`derived` or `internal` table every column has that class (or `internal`). In a `free` table,
version counters are `revision`, timestamps and server-owned values are `derived`, tokens and
hashes are `internal`, and the rest are `free`.

## What this means for the editor

1. **Character data is editable, offline only.** All `character_*` gameplay tables are loaded when the
   character enters the world and kept in memory; the server then writes back with compare-and-set on
   the revision counters (for example `character_base` position: `UPDATE ... WHERE position_revision =
   @storedRevision`, `PostgresCharacterCheckpointStore.Writes.cs:95-104`). An edit made while the
   character is online is either overwritten or makes the server's next write fail. Until the round2
   `/admin/capabilities` endpoints exist, "free" on a character table means "free while offline".
2. **Content the server runs is sealed.** Items, attributes, equipment ranks, materials, Holy Suit
   rules, pets, pet skills, Pet Unite, maps, monsters, spawns, NPCs, dialogues, classes, skills, talents,
   world bosses and the enter-bootstrap packets are *published revisions*: rows keyed by a SHA-256
   revision, a singleton `*_publication` pointer, triggers that reject UPDATE/DELETE, and a start-up
   loader that recounts and re-hashes everything and refuses to start on a mismatch
   (`docs/data-architecture-b20g-content-publication-capture-separation-20260801.md`). The editor
   must show these read-only and say why.
3. **The older "template" tables are staging copies.** `item_templates`, `item_attribute_templates`,
   `equipment_rank_rules`, `skill_templates`, `skill_book_templates`, `talent_templates`,
   `talent_effect_templates`, `class_templates`, `map_templates`, `map_address_points`, `map_links`,
   `monster_templates`, `world_boss_areas`, `pending_world_boss_areas` and the `npc_*_templates` are
   loaded only into an empty database to build the first revision
   (`PostgresRelationalContentBaselineBootstrapper`). Editing them changes nothing in game. Some of them
   still matter: `item_templates`, `skill_templates`, `talent_templates`, `pet_templates` and
   `pet_aptitude_templates` are **foreign-key targets** (`character_items.prop_id`,
   `character_skills.skill_id`, `character_talents.talent_id`, `character_pets.species_id`,
   `character_pets.aptitude`; each table's `referenced_by` lists all of them), so an id must exist
   there; and **`holy_suit_effect_templates.per_point` / `maximum` are read live** by the stat
   calculation (`State/PostgresCharacterRuntimeItemProjectionSql.cs:207-238`) despite the B20G doc
   calling the table staging-only.
4. **For the item / skill / pet libraries**, read the published rows: filter
   `item_template_content_definitions` on `revision = (SELECT revision FROM
   item_template_content_publication)` (3,488 items: 2,282 consumables, 350 mounts, 145 weapons, 138
   fashion, ...). The same pattern works for `gameplay_*` (one revision live) and `pet_content_*`.
   English names that the DB lacks (several `map_templates.display_name` are Chinese) come from the
   Origin client files (`catalog-origin/`).
5. **Tunable without code** (class `free`, not character data): drops (`monster_loot_tables`,
   `monster_loot_rules`), Medusa (`medusa_*_rules`, `medusa_instance_settings`,
   `medusa_pet_capture_rarity_weights`, `medusa_reward_title_definitions`), entries
   (`legacy_instance_settings`), quest payouts (`quest_reward_values`, `quest_reward_slots`), GM monster
   and NPC overrides (`gm_*`), boss critical resistance (`monster_combat_balance`), global monster EXP
   (`monster_reward_settings`), Holy Stone rolls (`holy_spirit_balance_settings`), Holy Suit set
   bonus (`holy_suit_effect_templates`), guild building costs (`guild_building_levels`), realms
   (`server`) and the RATES table (`server_rates`, hot). Check "applies": most need a restart.
6. **Evidence is read-only.** Ledgers, baselines, settlements, claims, audits and the instance reward
   records are either trigger-immutable or the thing that stops a reward from being paid twice.
7. **Warehouse size and pet hatch evidence are guarded.** `character_base.warehouse_capacity` may only
   change with a `warehouse_expansion_settlements` row (trigger); `character_pets` hatch columns are
   immutable after insert (trigger `guard_pet_hatch_rank_evidence`). README section 8.4 explains how
   the current editor handles both.

### Mounts

No table of its own. A mount is an item of kind `mount` (350 templates, ids 14220-16209) in `character_items`: the riding slot is equipment slot 20, mount gear is slots 15-19. Mount content is in `item_template_content_definitions`. The Ride status itself is session state, not stored.

## How each class was decided

* **sealed (content)**: the table has the trigger pair `guard_*_insert` + `reject_*_mutation`, or is a
  `*_publication` pointer with `validate_*_publication` + `reject_*_publication_delete` (trigger names are
  in each table's `triggers` list in the JSON). Loaders: `PostgresItemTemplateCatalogLoader*`,
  `PostgresPetContentReader*`, `PostgresPetOwnerMergeContentReader`, `PostgresPetLearnedSkillContentBootstrapper`,
  `PostgresWorldContentReaderLoader*` (all at start-up, `Program.cs` order in the B20G doc).
* **sealed (balance with CAS pointer)**: Faction Crier, Online Award and warehouse expansion: sealed
  revisions plus an audited pointer the workers pin at start-up (DB comments say so).
* **sealed (evidence)**: triggers `reject_character_economy_evidence_mutation`,
  `reject_monster_reward_settlement_mutation`, `reject_warehouse_immutable_mutation`,
  `reject_online_award_immutable_mutation`, `reject_command_audit_mutation`; or exactly-once claim tables
  whose primary key is the claim (quest reward slots, loot pickups, instance completions, Wonderland chests).
* **startup** for mutable settings: the snapshot readers are called once in

## Refreshing

1. Read-only snapshot of the live schema (one `BEGIN READ ONLY` transaction, ends with `ROLLBACK`):
   `ssh vps 'sudo -n -u postgres psql -X -q -v ON_ERROR_STOP=1 godswar' < snapshot.sql > live-schema-meta.json`
2. `python3 -I build_glossary.py --source /path/to/GodsWar`
   rewrites `glossary.json` and this file. It exits with code 1 when a live table has no entry in
   `glossary_tables.py`, or an entry names a table that no longer exists; `--check` only prints the report.
